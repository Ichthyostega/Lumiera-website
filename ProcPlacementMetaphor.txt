</p><h1 id="head-8680712df84abacc09b2d2cec0ecda56891cb6a6">Placement Metaphor used within the high-level view of Proc-Layer</h1>

<p></p>
<p>besides the <a href="http://www.pipapo.org/pipawiki/Cinelerra3/DesignProcess/ProcBuilder">Builder</a>, one of the core ideas of the Proc-Layer (as being currently implemented by Ichthyo) is to utilize <em>Placement</em>
as a single central metaphor for object association, location and
configuration within the high-level model. This means prefering <em>rules</em> over fixed values. </p>
<p>
</p><h2 id="head-f4a9bfacc9f245597df70e421d7660e74f5feec6">Description</h2>

<p></p>
<p>The basic idea is to locate <em>Media Objects</em> of various kinds within a <em>configuration space</em>.
Any object can have a lot of different properties, which may partially
depend on one another, and partially may be chosen freely. All these
various choices are considered as <em>degrees of freedom</em> -- and defining a property can be seen as <em>placing</em>
the object to a specific parameter value on one of these dimensions.
This view may be bewildering at first sight, but the important
observation is, that in many cases, we don't want to lock down any of
those parameters completely to one fixed value. Rather, we just want to
<em>limit</em> some parameters. </p>
<p>To
give an example, most editing applications let the user place a video
clip at a fixed time and track. They do so by just assigning fixed
values, where the track number determines the output and the layering
order. While this may seem simple, sound and pragmatic, indeed this
puts down way to much information in a much to rigid manner for many
common use cases of editing media. More often than not it's not
necessary to "nail down" a video clip, rather, the user wants it to
start immediately after the end of another clip, it should be sent to
some generic output and it should stay in the layering order above some
other clip. But, as the editing system fails to provide the means for
expressing such relationships, we are forced to work
with hard values, resort to a bunch of macro features or even
compensate for this lack by investing in production organisation (the
latter is especially true for building up a movie sound track). </p>
<p>Thus, using the <strong>Placement</strong> metaphor </p><ul>
<li>we have one single instrument to express the various kinds of relations </li>
<li>
<p>the <em>kind of placement</em> becomes an internal value of the placement </p></li>
<li>some kinds of placement can express rule-like relations in a natural fashion </li>
<li>while there remains only one single mechanism for treating a bunch of features in a unified manner </li>
<li>plugins could provide exotic and advanced placement kinds without the need of massively reworking the core. </li></ul>
<p>When interpreting the high-level model and creating the low-level model, Placements need to be <em>resolved</em>, resulting in a simplified and completely nailed-down copy of the session contents, which this design calls »the <strong>Fixture</strong>« </p>
<p>Media Objects can be placed </p><ul>
<li>fixed at a given time </li>
<li>relative to some reference time point given by another object (clip, label, timeline origin) </li>
<li>as plugged into a specific output pipe (destination port) </li>
<li>to a fixed layer number </li>
<li>layered above or below another reference object </li>
<li>fixed to a given pan position in virtual sound space </li>
<li>panned relative to the pan position of another object </li></ul>
<p>
</p><h4 id="head-5fd29128a78e613f56b92efaa04636b525774c61">Tasks</h4>

<p></p><ul>
<li>currently just the simple standard case is drafted in code. </li>
<li>the
mechanism for treating placements within the builder is drafted in
code, but needs to be worked out to see the implications more clearly </li></ul>
<p>
</p><h3 id="head-6061fbaa5841bb17c825f037084cf2a21d0eb681">Pros</h3>

<p></p><ul>
<li>one grippy metaphor to rule them all </li>
<li>includes the simple standard case </li>
<li>unified treatment </li>
<li>modular and extensible </li>
<li>allows
much more elaborate handling of media objects then the conventional
approach, while both the simple standard case and the elaborate special
case are "first class citizens" and completely integrated in all object
treatment. </li></ul>
<p>
</p><h3 id="head-30ccfb1d3951ebb0a822b00612c72d38a3adaf91">Cons</h3>

<p></p><ul>
<li>difficult to grasp </li>
<li>requires a separate resolution step </li>
<li>
<p>requires to <em>query</em> for object properties instead of just looking up a fixed value </p></li>
<li>forces the GUI to invent means for handling object placement which may go beyond the conventional </li>
<li>can create quite some surprises for the user, especially if he doesn't care to understand the concept up front </li></ul>
<p>
</p><h3 id="head-12897e1138bf74f9f1b2ab969899a8dc64409cdc">Alternatives</h3>

<p></p>
<p>Use the conventional approach </p><ul>
<li>media objects are assigned with fixed time positions </li>
<li>they are stored directly within a grid (or tree) of tracks </li>
<li>layering and pan are hard wired additional properties </li>
<li>implement an additional auto-link facility to attach e.g. sound to a video clip </li>
<li>implement a magnetic snap-to for attaching clips seamless after each other </li>
<li>implement a splicing/sliding/shuffling mode in the gui </li>
<li>provide a output wiring tool in the GUI </li>
<li>
<p>provide macro features for this and that.... (hopefully I made clear by now <em>why</em> I don't want to take the conventional approach) </p></li></ul>
<p>
</p><h2 id="head-0d9edeb9caf4306e1638722bd2c827f4626e9ee1">Rationale</h2>

<p></p>
<p>The
high-level model is close to the problem domain, it should provide
means to express the (naturally complex) relationships between media
objects. Using an abstract and unified concept is always better then
having a bunch of seemingly unrelated features. Moreover, the Placement
concept deliberately brings in an rule based approach, which well fits
into the problem domain. Besides, there is sort-of a visionary aspect
involved here too: Ichthyo thinks that nowadays, after image and sound
are no longer bound to physical media, there is potential for new
workflows to be discovered, and the Placement concept could be an
extension point for such undertakings. </p>
