</p><h1 id="head-8aeab1ad6e074576ab67e908c594dac0c2a98217">Cinelerra-3 Project Proposal</h1>
<span class="anchor" id="line-4"></span><p class="line867"><span class="u">May 2007</span>:
much of this is rather vapourware at the time of this writing. Just,
there seems to be some momentum in the Cinelerra community at the
moment. <br>
 <span class="anchor" id="line-5"></span>And there ist
the existing codebase. It is huge. It contains lots of know-how. But
any developer of some experience can easily see that it is the root for
some of the current problems Cinelerra is struck with. All of this
problems are rather indirect in nature. To make it clear: the state of
the current code base is satisfactory, it is well maintained. But it is
difficult to extend, tedious to analyze and it is lacking the
infrastructure needed to accomodate the demands users are putting on
such an application nowadays. If we would just go ahead pragmatically
and add all the sensible feature requests, like expandable tracks, more
drag-n-drop, more object-like behaviour of the assets, effects linked
to clips, sound linked to clips, individual keying of plugin
parameters, complete user-defineable ordering of the elements in the
render pipeline, a full-blown dvd-export editor, asset management and
searching features, transparent proxy editing, meta-clips, support for
larger projects with multiple timelines, etc -- adding all those
features <em>will kill the existing Codebase for sure.</em>  <span class="anchor" id="line-6"></span><span class="anchor" id="line-7"></span></p><p class="line874">But
things are not hopeless. Cinelerra is not alone, other Applications
have seen this problems, other Applications have advanced. <span class="anchor" id="line-8"></span><span class="anchor" id="line-9"></span></p><ul><li><p class="line862">we should not stick to a programming style that was <em>up to date </em>20 Years ago <span class="anchor" id="line-10"></span></p></li><li><p class="line862">we should utilize all the <em>experience, wisdom and craftmanship </em>gained in the last years by the developer community <span class="anchor" id="line-11"></span></p></li><li><p class="line862">we should rely more heavily on external libs for all things that are <em>not specific to video editing</em> <span class="anchor" id="line-12"></span></p></li><li><p class="line862">we should adopt <em>well proven methods</em> and <em>»best practices«</em> <span class="anchor" id="line-13"></span></p><ul><li><p class="line862">Encapsulation, programming against Interfaces. <a href="http://www.pipapo.org/pipawiki/Cinelerra/Developers/ichthyo/best_practices">This means for Cinelerra...</a> <span class="anchor" id="line-14"></span></p></li><li><p class="line862">Decoupling of Components by making them self-contained  <a href="http://www.pipapo.org/pipawiki/Cinelerra/Developers/ichthyo/best_practices#head-eded60c0ad33d351c0dd2711c16008190fb39302">(this means..)</a> <span class="anchor" id="line-15"></span></p></li><li><p class="line862">Composition over Inheritance <a href="http://www.pipapo.org/pipawiki/Cinelerra/Developers/ichthyo/best_practices#head-6140d5c520ed00cbcb077973a716fad9b23d2635">(more..)</a> <span class="anchor" id="line-16"></span></p></li><li><p class="line862">Strong Typing and the use of Design Patterns <a href="http://www.pipapo.org/pipawiki/Cinelerra/Developers/ichthyo/best_practices#head-151eea0df837eadd5e2c771c0d2b93186383f949">(more..)</a> <span class="anchor" id="line-17"></span></p></li><li><p class="line862">Design by Contract and wide use of Assertions <a href="http://www.pipapo.org/pipawiki/Cinelerra/Developers/ichthyo/best_practices#head-782a47b9d92651190cf54b7f4583b03a151535c9">(more..)</a> <span class="anchor" id="line-18"></span></p></li><li>Frequent Refacturing combined with a Stable Branch <span class="anchor" id="line-19"></span></li><li><p class="line862">Unit Testing <a href="http://www.pipapo.org/pipawiki/Cinelerra/Developers/ichthyo/best_practices#head-6b45f7492671dcb9227aff7d4f8726ece2ea7c69">(more..)</a> <span class="anchor" id="line-20"></span></p></li></ul></li></ul><p class="line867"><br>
 <span class="anchor" id="line-21"></span><span class="anchor" id="line-22"></span></p><p class="line867"><br>
 <span class="anchor" id="line-23"></span>
</p><h2 id="head-10f21f0b1e4492b803d192d9d8470fbcc8f68e08">But won't this be a new Application?</h2>
<span class="anchor" id="line-24"></span><p class="line862">No, it won't, because we don't want a new application. We want it basically to stay the same.<br>
 <span class="anchor" id="line-25"></span>The
concepts embodied into Cinelerra are clean and stright forward. It is
format-agnostic, quality oriented, targeted at pro work.<br>
 <span class="anchor" id="line-26"></span>The phillosophy is right. It has good Karma. <img alt=";-)" src="Cin3_Project_Proposal_files/smile4.png" title=";-)" height="15" width="15"> <span class="anchor" id="line-27"></span><span class="anchor" id="line-28"></span></p><p class="line862">So, everything should be done in a manner that doesn't fundamentally break the existing codebase.<br>
 <span class="anchor" id="line-29"></span>We don't want to start out from scratch, we want a transition and a reworking.<br>
 <span class="anchor" id="line-30"></span>At every Milestone, there should be a usable and almost feature-complete Application.<br>
 <span class="anchor" id="line-31"></span><span class="anchor" id="line-32"></span></p><p class="line867">
</p><h2 id="head-ae85e38976d1be2c7bd29a063f6f3bc3328cabf0">Architecture</h2>
<span class="anchor" id="line-33"></span><p class="line862">The Current Cinelerra has an Architecture. Well, sort of. There is a backend region (libquicktimehv, libmpeg). <br>
 <span class="anchor" id="line-34"></span>There are the virtual nodes and plugins of the render engine, and there is the guicast lib with its window and widget classes.<br>
 <span class="anchor" id="line-35"></span>And thats all of it. <em>Architecture is not a reality at the code level.</em> We should most definitively change this. <span class="anchor" id="line-36"></span><span class="anchor" id="line-37"></span></p><p class="line862">The existing functionaliy should be separated into <span class="u">three layers</span>: Backend, Core, GUI.<br>
 <span class="anchor" id="line-38"></span>Or -- slightly changed viewpoint -- separated into <span class="u">five independent functional Units</span>: <span class="anchor" id="line-39"></span></p><ol type="1"><li>data handling backend <span class="anchor" id="line-40"></span></li><li>object manipulation (EDLs/cuts/plugin-instances/automation) <span class="anchor" id="line-41"></span></li><li>render engine (render-pipeline/plugins/mixing/playback/rendering) <span class="anchor" id="line-42"></span></li><li>asset management <span class="anchor" id="line-43"></span></li><li>user interface <span class="anchor" id="line-44"></span><span class="anchor" id="line-45"></span></li></ol><p class="line874">Each
of this units is self-contained as much as possible. They cooperate
using only well defined and more or less fixed Interfaces. <span class="anchor" id="line-46"></span>Each of this Interfaces builds upon one <em>key abstraction,</em> which should be choosen/designed to be just powerfull enough to encompass <span class="anchor" id="line-47"></span>and
express all interactions going on at this Interface. For example,
render engine and data backend are just talking about media <span class="anchor" id="line-48"></span>streams.
Render engine retrieves playlists from the object manipulation
component, while this one loads and queries assets (clips, <span class="anchor" id="line-49"></span>whole sessions, effects, plugins) from the asset manager. And the GUI just sends and recieves events from the core engine. <span class="anchor" id="line-50"></span>As a spin off product, most of the components could be usefull as such. The data handling backend and the asset management <span class="anchor" id="line-51"></span>could
be scriptable, e.g. via python bindings. Object manipulation and render
engine could work in a headless fashion (commandline client) <span class="anchor" id="line-52"></span><span class="anchor" id="line-53"></span></p><p class="line862">Read more on the proposed <a href="http://www.pipapo.org/pipawiki/Cinelerra/Developers/ichthyo/Cinelerra3/Architecture">core Components and Interfaces</a>... <span class="anchor" id="line-54"></span><span class="anchor" id="line-55"></span><span class="anchor" id="line-56"></span></p><p class="line867"></p><hr><p class="line874"> <span class="anchor" id="line-57"></span>
</p><h2 id="head-3d76192cd220a2cba4457f3591649dc59e89a28a">Roadmap</h2>
<span class="anchor" id="line-58"></span><p class="line874">All of this
sounds ambitious and contradictory to the aforementioned goal of
allways having a usable and almost complete application. <span class="anchor" id="line-59"></span>But it is doable, serious. And, with the exception of one (final) step, namely rewriting the GUI, it doesn't require excessive <span class="anchor" id="line-60"></span>developer manpower or overly much specialized skills. Why? <em>Because we don't need to re-invent functionallity</em> -- we always have <span class="anchor" id="line-61"></span>a working piece of code and have <em>just</em> to break it out and transform it into the new structures. <span class="anchor" id="line-62"></span><span class="anchor" id="line-63"></span></p><p class="line862">Don't get me wrong: this <em>is</em> a proposal, a draft, sort of brainstorming.<br>
 <span class="anchor" id="line-64"></span>Just to show that it's feasible, I'll detail on a complete project plan with milestones. <span class="anchor" id="line-65"></span><span class="anchor" id="line-66"></span></p><p class="line867">
</p><h3 id="head-02271108944219b6a2af2fe9941801f438a0f393">Milestone-1: whetting of tools</h3>
<span class="anchor" id="line-67"></span><div><table><tbody><tr style="background-color: rgb(255, 255, 224);">  <td style="text-align: right;"><p class="line862">abstract </p></td>
  <td><p class="line862"> <strong>bring in proper tools and frameworks</strong> </p></td>
</tr>
<tr>  <td style="text-align: right;"><span class="anchor" id="line-68"></span><p class="line862"> criteria                    </p></td>
  <td><p class="line862"> we <em>feel</em> well equipped for the battle <img alt=":)" src="Cin3_Project_Proposal_files/smile.png" title=":)" height="15" width="15"> </p></td>
</tr>
<tr>  <td style="text-align: right;"><span class="anchor" id="line-69"></span><p class="line862"> user-visible impact         </p></td>
  <td><p class="line862"> backported fixes for bugs spotted by the new tools </p></td>
</tr>
</tbody></table></div><dl><dt>motivation</dt><dd><span class="anchor" id="line-71"></span>just don't rely solely on common sense and handwork, bring in proven tools and methods. <span class="anchor" id="line-72"></span></dd><dt>description</dt><dd><span class="anchor" id="line-73"></span>some facilities are better to setup beforehand. This includes quite some "chainsaw surgery", <span class="anchor" id="line-74"></span>but we shouldn't get too much into individual technical details. Mostly, it's about selecting <span class="anchor" id="line-75"></span>and integrating library solutions for some of the common problems, like multithreading and locking. <span class="anchor" id="line-76"></span><p class="line862">Further, we need diagnostic tools and a framework for assertions and quality management (<a href="http://www.pipapo.org/pipawiki/NoBug">NoBug</a>, Valgind,...).<br>
 <span class="anchor" id="line-77"></span>We need an up-to-date, configurable Logging/Reporting System, and we should set up a basic Unit Testing <span class="anchor" id="line-78"></span>framework (at least for the new code to-be-written; it is clear that we can't do Test Driven Developement <span class="anchor" id="line-79"></span>in its pure form). Moreover, any improvements to the build system are welcome, and we should establish a <span class="anchor" id="line-80"></span>framework of GIT branches, build scripts and repos to be able to roll out beta versions to the users <span class="anchor" id="line-81"></span>without much effort. (We can't do TDD, so we need the users, hehe!) <span class="anchor" id="line-82"></span></p></dd><dt>problems</dt><dd><span class="anchor" id="line-83"></span><p class="line862">the
runtime behaviour of the current Cinelerra app is quite frightening. It
creates lots and lots of threads, uses a locking scheme obviousely
broken, and it segfaults on a regular base. <em>We need to stop this.</em> Cinelerra is inteded to be for professional work. With respect to this pretension, the current state is plain ridiculous.  <span class="anchor" id="line-84"></span></p></dd><dt>solution aproach</dt><dd><span class="anchor" id="line-85"></span><p class="line862">Twofold.
Bring in some tools and spot some of the most obvious problems. Replace
some of the homebrew solutions with state-of-the-art libraries. Try to
get some of this backported to Cinelrra-CV. This is to immediately
prove the usefullness of our undertakings and give our faithfull users
an immedate value payback.<br> Besides, select some further libraries,
tools and methods usable only in conjunction with a partial
reorganization of the code base. This is only preparatory at the moment
but will give us the ability to get a really reliable codebase, if at
all we choose to proceed on this path... <span class="anchor" id="line-86"></span></p></dd><dt>goals</dt><dd><span class="anchor" id="line-87"></span><p class="line862">Nothing dramatic. The same code base. Some additional dependencies <img alt=":\" src="Cin3_Project_Proposal_files/ohwell.png" title=":\" height="15" width="15"> , some spotted bugs. <img alt=":-?" src="Cin3_Project_Proposal_files/tongue.png" title=":-?" height="15" width="15"> <br>
 Maybe having gained some approvement by the Community <span class="anchor" id="line-88"></span><span class="anchor" id="line-89"></span></p></dd></dl><p class="line867"><br>
 <span class="anchor" id="line-90"></span><span class="anchor" id="line-91"></span></p><p class="line867">
</p><h3 id="head-4deb678f4a3ddda0b9371751cced3bfd2f25eea4">Milestone-2: laying the foundations</h3>
<span class="anchor" id="line-92"></span><div><table><tbody><tr style="background-color: rgb(255, 255, 224);">  <td style="text-align: right;"><p class="line862">abstract </p></td>
  <td><p class="line862"> <strong>design the key abstractions and the data backend</strong> </p></td>
</tr>
<tr>  <td style="text-align: right;"><span class="anchor" id="line-93"></span><p class="line862"> criteria                    </p></td>
  <td><p class="line862"> we can draft all neccessary interfaces and express the main calls in a natural way </p></td>
</tr>

Moreover, it is <em>the</em> reality test par excelance: if our ideas,
design principles, foundations and abstractions aren't sound, then
performance and stability will be worse then at current. Quality is
measurable here. <span class="anchor" id="line-120"></span></p></dd><dt>description</dt><dd><span class="anchor" id="line-121"></span><p class="line862">the rendering pieline consists of processing nodes and works in pull processing mode. We won't change this.<br>
But we want to remove the "special role" some of the nodes are playing
at the moment, namely the mask, the camera, the fader, the projector.
Another central point is the <em>Builder-Pattern</em>:
the current code is organized vaguely by this pattern, but it is not
really implemented this way. This causes a mix of several concerns and
causes the rendering codepath to be polluted with lots of conditional
tests and decisions which aren't strictly video prcessing related. This
is again an example of "missing the spirit of the concept": typically
that's just why you want to apply the Builder pattern. Without that
incentive, it would be much more transparent to use table-style
programming.<br>
So the idea here should be that the augmented object manipulation
component (i.e. the EDL and such) does the building and delivers a
completely configured render pipelline (object graph) to the rendering
engine. To be more precise: it could be a list of render pipelines, one
for each constantly configured segment of the session. No need to build
up the objects for every frame. No need to do any color model decisions
within the inner processing loop and no need to test for objects
disappearing due to editing activties in the course of playback, not to
mention handling of specific hardware like BUZZ-support. Just one
central solution for hot-swapping the render pipeline for one segment
of the session is needed. So my guess is, finally 3/4 of the code
presently there will simply disappear. <span class="anchor" id="line-122"></span></p></dd><dt>problems</dt><dd><span class="anchor" id="line-123"></span>the current implementation  <span class="anchor" id="line-124"></span><ol type="a"><li>is rather directly integrated with playback and background rendering <span class="anchor" id="line-125"></span></li><li>the nodes are built up for each frame while rendering <span class="anchor" id="line-126"></span></li><li>what to do with all the existing plugin code <span class="anchor" id="line-127"></span></li></ol></dd><dt>solution aproach</dt><dd><span class="anchor" id="line-128"></span><p class="line862">Introduce a new controller component, the <a class="nonexistent" href="http://www.pipapo.org/pipawiki/RenderManager">RenderManager</a>. behaves identical to the current Cinelerra rendering code: it builds up
a rendering pipeline for each frame by directly accessing EDL and clip
objects. But, at least, we alredy use the new data backend functions --
the newly created render pipeline nodes are cleanly separated from the
Builder, as well from the backend complexities and they do <em>nothing but rendering</em>. This solves (b).<br>

My idea for a new Cinelerra is: <span class="anchor" id="line-220"></span></p><ul><li>to see something more stable rather than a whole raft of improvements <span class="anchor" id="line-221"></span></li><li>to see code that is easier to modify and enhance. <span class="anchor" id="line-222"></span></li></ul><p class="line874">I
think being too ambitious is highly likely to lead in failure. What I
propose is that we identify one key area of Cinelerra that needs
addressing, and make that the target of Cinelerra 3.0. <span class="anchor" id="line-223"></span></p><ul><li style="list-style-type: none;"><p class="line862">-- <a href="http://www.pipapo.org/pipawiki/MarkCarter">MarkCarter</a> 2008-03-06 05:25:10 <span class="anchor" id="line-224"></span><span class="anchor" id="line-225"></span></p></li></ul><p class="line862">I
would love to agree, but systematic migration is not always possible or

spending more time working around the problems than writing new code.

development is moving <em>much</em> more quickly. <span class="anchor" id="line-226"></span></p><ul><li style="list-style-type: none;"><p class="line862">- <a class="nonexistent" href="http://www.pipapo.org/pipawiki/RobScott">RobScott</a> 2008-02-07 17:30:00 <span class="anchor" id="line-227"></span><span class="anchor" id="line-228"></span></p></li></ul><p class="line862">Yes, that's pretty much the conclusion we reached meanwhile too.
